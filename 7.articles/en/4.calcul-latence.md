# Latency Calculation and Master-Slave Synchronization: Behind the Scenes of "Master Sync"

In a distributed system like **GroovyMorning**, where audio captured by a Java recorder is analyzed by a Python segmenter, synchronization is a constant challenge. The **Master Sync** mechanism was designed to ensure exact correspondence between the Java stream and the Python segmenter.

## The Problem: Stream Drift

Several factors introduce lag (latency) between two servers listening to the same radio stream URL:
- Variations in HTTP caching delays.
- The precise startup time of each `ffmpeg` process.
- The impact of CPU load on buffer reading speed.

Without recalibration, a lag of several seconds could affect the final recording during AI detection.

## The Solution: On-the-fly Audio Fingerprinting

A simplified acoustic fingerprinting technique is used to calculate the actual offset between the two instances. The technical process unfolds as follows:

### 1. Fingerprint Generation (Java Side)
The Java recorder waits for the first segments of the continuous recording to be written to disk. As soon as segment No. 5 is available (approximately 5 seconds after startup), a fingerprint is extracted:
- **Extraction**: Conversion of segments into raw audio (16-bit PCM) via FFmpeg.
- **Downsampling**: Reduction of the audio to **4000 Hz mono** to limit data size.
- **Result**: A compact binary file (`fingerprint.raw`) representing 2 seconds of sound.

### 2. The Synchronization Request (`/api/sync_offset`)
This binary is transmitted via a POST request to the Python segmenter, accompanied by the information `positionInSeconds=5`. This indicates to the Python segmenter the state of the audio on the Java side at instant T=5s.

### 3. Delta Calculation (Python Side)
A **rolling buffer** (circular buffer) of the audio being processed is maintained by the Python segmenter. Upon receiving the fingerprint:
- A comparison is made between the received fingerprint and the buffer data.
- The point of maximum correlation is sought to identify the exact offset.
- **The Delta**: A confidence score and a `delta` are returned. For example, a delta of `3.45` indicates that the Java stream is 3.45 seconds behind the Python stream.

### 4. Applying Recalibration
The `delta` received by the Java recorder is stored in the `masterOffsetSeconds` variable. 
- **Start Correction**: Upon a "START" notification, Java adjusts the recording start time by integrating this delta.
- **Precision**: Synchronization is only validated if the confidence score is high (> 0.7), avoiding any erroneous synchronization on noise or silence.

## Why Not Just Use System Time?

While system time (NTP) synchronizes clocks, it does not guarantee synchronization of the stream **content**. A radio stream may have a variable delay due to distribution servers (CDNs). Fingerprinting proves to be the only reliable method to ensure a cut based on the sound content actually perceived on both sides.

This "Master Sync" mechanism allows GroovyMorning to achieve high precision in chronicle extraction.
