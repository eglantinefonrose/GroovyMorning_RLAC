# High Availability Audio Capture: The 24/7 Challenge in Java

In the GroovyMorning project, the `RLAC-AudioRecorder` module is the heart of the system. Its mission is critical: capturing the radio stream without interruption, 24 hours a day, and transforming this raw stream into segments usable by a mobile application.

## Why Java for Capture?

While Python is excellent for AI, Java (via Spring Boot) was preferred for the capture part for several reasons:
*   **Thread Management**: Handling streams and external processes (FFmpeg) requires robust concurrency management.
*   **Stability**: The JVM offers memory management suitable for processes intended to run uninterruptedly.
*   **Ecosystem**: Integration with schedulers (Quartz) and databases is mature and performant.

## The "Master Stream" and "Dynamic Recording" Concept

Rather than starting a recording at the precise moment a chronicle begins (which would risk missing the first few seconds due to connection latency), a two-stage system was implemented.

### 1. Master Stream (Continuous)
An FFmpeg process runs continuously. It generates 1-second **fMP4** segments. This rolling buffer allows the AI to analyze the near past and the system to "go back in time" to capture the exact start of a chronicle.

### 2. Dynamic Segmentation
When a "START" notification is issued by the AI engine, the Java server does not start a new recording. It begins creating links (symlinks) or copying segments already generated by the Master Stream to a folder specific to the chronicle. This is the principle of **Dynamic Recording**.

## Mastering FFmpeg via Java

FFmpeg control is performed via `ProcessBuilder`. The standard output is monitored to detect stream errors (internet connection loss, bitrate change) and automatically restart the process if necessary.

```java
// Simplified process monitoring example
ProcessBuilder pb = new ProcessBuilder("ffmpeg", "-i", streamUrl, ...);
Process process = pb.start();
// Active monitoring in a separate thread
```

## Error Management and Robustness

To guarantee high availability, several mechanisms have been put in place:
*   **Safety Timeouts**: If no chronicle end notification is received (in case of an AI bug), a safety timeout stops the recording to avoid disk saturation.
*   **Auto-reconnect**: In case of a network outage, the system attempts exponential reconnections.
*   **Automatic Cleaning**: A maintenance service deletes Master Stream segments older than one hour, keeping only elements archived as "chronicles."

## Result
This system achieves high capture reliability. Even if the AI service is momentarily unavailable, the continuous stream remains active, allowing for post-hoc analysis to recover missing segments.
