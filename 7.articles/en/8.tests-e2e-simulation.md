# End-to-End (E2E) Testing: Simulating a Radio to Validate the Pipeline

Developing a system combining Java, Python, FFmpeg, databases, and AI models requires special attention to stability. To ensure that changes do not impact overall functioning, a **Simulation** environment was established.

## Testing Philosophy in GroovyMorning

Unit tests, while necessary, prove insufficient to validate the "life cycle" of a chronicle. An **End-to-End (E2E)** test environment, completely isolated under Docker, was therefore created.

## Live Radio Simulation

The major challenge lies in the "Live" aspect. Waiting for an actual broadcast on France Inter to test the code is avoided through the use of a reference audio file (`test_flux.wav`). This file contains:
1.  Silence passages.
2.  A real jingle.
3.  A spoken sequence.
4.  An ending jingle.

This file is injected into the system via a **Unix pipe** (`/tmp/audio_pipe`), simulating live radio stream behavior for the services.

## Orchestration with Docker Compose

A complete infrastructure is deployed in seconds for each test execution:
*   **Postgres**: Storage for test schedules.
*   **GMFM-Recorder (Java)**: Capture testing.
*   **GMFM-Segmenter (Python)**: AI testing.
*   **Test Runner (Python)** : Overall coordination.

## Test Scenario

The `test_runner.py` script executes the following steps:
1.  **Initialization**: Injection of a dummy schedule into the database.
2.  **Injection**: Starting playback of the `test_flux.wav` audio file.
3.  **Monitoring**: Regular interrogation of the Java API to detect the appearance of a new chronicle.
4.  **Validation**: Verification of the `.m3u8` file generation on disk and correspondence of its duration with the injected data.

## Pipeline Benefits

This test pipeline allows for:
*   **Regression Validation**: Ensuring that optimizations do not hinder communication between components.
*   **Edge Case Testing**: Verifying behavior during connection outages or slight jingle modifications.
*   **Cloud Independence**: Local execution avoids API costs (like DeepSeek) for frequent tests, thanks to the use of "mocks" or lightweight local models.

## Conclusion

The simulation approach secures GroovyMorning deployment. Each modification is validated by a real radio simulation, ensuring chronicle availability for the end user.
